# Web 运营后台开发规范

## 适用范围与技术栈

- 本文件适用于 `frontend/web/`。
- 技术栈：Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus、Tailwind CSS v4、SCSS、Vitest。
- 包管理器以 `package.json` 的 `packageManager` 为准，统一使用 pnpm。不要用 npm 安装依赖，也不要无意更新遗留的 `package-lock.json`。
- 当前页面是喻信招投标产品的内部运营后台，不是 FastApiAdmin 演示站。新增页面应围绕真实运营任务设计。

## 目录与职责

- `src/api/`：按后端模块封装请求和请求/响应类型。
- `src/views/`：路由页面与页面私有组件。
- `src/components/`：可跨页面复用的通用组件，优先复用现有 `Fa*` 组件。
- `src/layouts/`：全局布局，不在业务需求中随意改动。
- `src/store/`：Pinia 状态；只有跨页面或需要持久化的状态才进入 Store。
- `src/config/setting.ts`：主题、布局及产品默认设置的来源之一。
- `src/styles/`：全局 token、Element Plus 覆盖、明暗主题和页面公共样式。

## Vue 与 TypeScript

- 新组件使用 `<script setup lang="ts">` 和 Composition API，保持单向数据流。
- Props、Emits、表单、表格列、API 参数和响应必须有明确类型；不要因为方便扩大 `any` 的使用。
- 页面私有逻辑优先放在页面目录内；只有出现真实复用点时再提取全局 composable 或组件。
- 避免巨型页面继续膨胀。复杂表单、抽屉、表格单元和业务面板应拆成语义明确的组件。
- 沿用 `@/`、`@utils` 等现有别名，不新增意义重复的导入路径。

## API、权限与状态

- API 请求集中写在 `src/api/`，统一使用 `@utils` 导出的 `request`；页面组件不得自行创建 Axios 实例。
- 沿用全局 `ApiResponse<T>`、`PageResult<T>` 和现有分页字段，不在页面里手工猜测响应结构。
- 成功和常规失败提示由请求拦截器统一处理。除非交互有额外业务含义，不要重复弹出成功/失败消息。
- 新增按钮和操作时复用现有权限指令/权限码模式；前端隐藏不是安全边界，后端必须同步鉴权。
- 明确处理加载、空数据、错误、禁用、重复提交和权限不足状态。
- 认证、刷新令牌、用户信息、头像和静态资源 URL 属于桌面端共享契约，修改前要核对后端及桌面端调用。

## 界面与交互

- 优先沿用现有列表页结构：搜索区、表格卡片、工具栏、分页、抽屉/对话框，保持间距和交互一致。
- 一个动作只保留一个清晰入口；不要为装饰堆叠图标、标签、说明文字或重复按钮。
- 能在一行清晰表达的信息不要拆成多行。辅助说明只在能降低误操作或解释复杂业务时出现。
- 图标必须表达真实语义，并优先复用项目现有 Iconify/Element Plus 图标；不要给每个普通标题机械添加图标。
- 危险操作需要明确对象、二次确认和可理解的结果提示。
- 表单标签、按钮、状态名和错误文案使用简洁中文；同一概念在不同页面保持同名。
- 页面应在常见桌面分辨率下可用，窄窗口不应出现不可操作的横向溢出。

## 浅色、深色与主题

- 所有新页面和组件必须同时支持浅色、深色及跟随系统模式。默认逻辑位于 `src/config/setting.ts`，不要另建第二套主题状态。
- 优先使用 `src/styles/tailwind.css` 中的语义 token，例如 `bg-box`、`bg-(--app-bg)`、`text-g-*`、`border-(--default-border)`、`text-theme`，以及 Element Plus 的 `--el-*` 变量。
- 使用 Tailwind `dark:` 变体或现有 `.dark` 作用域处理模式差异。不要在业务组件中用固定的 `#fff`、`#000`、浅灰背景冒充语义色。
- 如果确实需要新的颜色，先在全局样式中定义成对的浅色/深色语义变量，再由组件引用；不要散落魔法色值。
- 图表使用现有 `useChart` 和主题监听方式，主题切换后必须同步更新坐标轴、提示框、边框、文字和空状态。
- 模态框、抽屉、下拉层、悬浮态、禁用态、边框和阴影也属于主题验收范围，不能只检查页面背景。
- 修改主题系统时检查 `index.html` 的首屏主题恢复、`src/config/setting.ts`、`src/store/modules/setting.store.ts` 和 `src/styles/`，避免首屏闪烁或持久化失效。

## 样式与格式

- 遵守现有 Prettier：双引号、分号、2 空格、100 列。
- 优先使用现有 utility class 和设计 token；业务页局部样式使用 scoped SCSS，避免高权重全局覆盖。
- 不随意使用 `!important`。如果现有组件覆盖必须使用，限制选择器范围并说明原因。
- 不通过复制大段相似 CSS 创建“新风格”；先检查相邻页面和公共组件。

## 验证命令

在 `frontend/web/` 下按改动范围执行：

```powershell
pnpm type-check
pnpm test
pnpm build
```

- `pnpm lint` 会包含自动修复和格式化，执行前确认不会造成全仓无关变更；必要时只对改动文件运行对应工具。
- 纯 UI 修改除自动检查外，至少人工检查目标页面的浅色、深色、加载、空数据和窄窗口状态。
- 依赖发生变化时提交 `pnpm-lock.yaml`；没有依赖变化不要刷新锁文件。
