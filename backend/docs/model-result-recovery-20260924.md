# 模型成功结果与结算恢复

## 根因

092401 的请求在供应商响应体完整返回后，运营端结算出现 `TimeoutError`。
此前生成和结算共用异常分支，收尾异常被映射为模型总时限超时 `50401`。
已有日志能确定阶段，不能确定数据库等待发生在连接建立、连接池还是 SQL 执行。

## 文件职责

```text
app/api/v1/module_model_gateway/
├── gateway.py              # 成功后的保存/结算与模型失败分类分离
├── result_journal.py       # 私有加密恢复文件、请求归属、租约与保留期
├── settlement_recovery.py  # 冻结计费输入，只重试结算
├── settlement_worker.py    # 服务启动后恢复未结算结果，定期有限重试
└── stream_result.py        # 汇总已完成的流式结果和工具调用，支持重放
```

## 行为

1. 付费调用前登记 `(app_id, request_id)`，校验本人身份和内容指纹。同一请求并发提交只允许一个执行者。
2. 上游成功后先加密保存输出、用量和冻结的计费配置，再结算。模型失败的异常分支不包含成功后的收尾。
3. 结算等待默认 10 秒；失败时返回原输出，`settlement_status=PENDING`、`charged_credits=null`。这不是模型等待上限，也不表示免费。
4. 后台每 30 秒检查，失败间隔至少 60 秒，同一结果最多尝试结算 12 次。中断后的租约 300 秒到期可恢复；多进程通过同一本地文件协作。
5. 同一身份、编号和完全相同请求再次提交，读取已保存结果，只补结算，不重发模型。流式重放为完整结果，调用方应替换该请求原显示内容，不能把两次完整输出拼接。
6. PostgreSQL 事务先锁积分账户，再检查既有用量。提交成功但确认丢失时返回原金额，不重复扣款、用量或任务证据。
7. 模型运行鉴权完成后释放只读事务，避免跨越模型等待并在响应后提交失效连接。

## 配置与数据保护

- `MODEL_RESULT_JOURNAL_PATH`：默认 `backend/data/model-results.sqlite3`。必须是私有、可写、本地持久目录，不能放在静态资源目录。
- `MODEL_RESULT_RETENTION_DAYS=7`：已结算输出到期清除密文，保留编号墓碑阻止重复生成。未结算输出不按此期限删除。
- `MODEL_SETTLEMENT_TIMEOUT_SECONDS=10`：只限制结算，原模型等待、单次输出和上下文配置不变。
- 输出采用现有 `SECRET_KEY` 派生的 Fernet 密钥加密。不保存原始提示词、供应商密钥或地址。输出可能包含业务原文，必须按敏感数据管理。
- Docker 为 `/home/data` 配置独立持久卷，Git 和镜像构建排除此数据。备份须同时保留数据与匹配密钥；直接轮换密钥会导致旧密文无法读取。
- 适用单机多进程。多机独立目录不提供跨节点生成幂等，需另行设计共享可靠存储；不要在锁语义不可靠的网络盘使用 SQLite。

## 边界与故障处理

- 调用前保存服务不可用：返回友好 `50306`，不调用付费模型。
- 成功后磁盘故障或结果尚未落盘时强制终止：不能保证恢复未保存结果。保留请求待核对，禁止自动重复生成，不伪装为模型超时。
- 结算次数耗尽、预占已取消、既有记录冲突或密文损坏：保留待核对状态，不盲目重试或清零；运营需核对账目。
- 未完整结束的流继续返回中断。历史故障未保存的输出不能由本修复补回。
- 原账务回执接口继续以 PostgreSQL 事实为准；补结算期间可为 `UNKNOWN/RESERVED`，不能伪造已结算回执。
