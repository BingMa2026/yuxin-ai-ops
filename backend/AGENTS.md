# FastAPI 后端开发规范

## 适用范围与技术栈

- 本文件适用于 `backend/`。
- 技术栈：Python 3.12+、FastAPI、Pydantic v2、SQLAlchemy 2 异步 ORM、Alembic、PostgreSQL、Redis、pytest、Ruff。
- 使用 `uv` 管理本地环境和命令；新增或升级依赖时同步维护 `pyproject.toml`、`uv.lock`，生产依赖还要核对 `requirements.txt`。
- PostgreSQL 是喻信当前实际运行数据库。框架虽保留 MySQL/SQLite 适配，新业务 SQL 和迁移必须首先在 PostgreSQL 语义下正确。

## 模块结构

新业务模块沿用现有按领域竖切的结构：

```text
module_xxx/
├─ controller.py   HTTP 路由、依赖和参数接入
├─ service.py      业务规则与事务编排
├─ crud.py         数据访问
├─ model.py        SQLAlchemy ORM 模型
├─ schema.py       Pydantic 输入/输出模型
└─ param.py        查询参数（模块需要时）
```

- Controller 保持薄，只做协议转换、依赖注入和响应返回。
- Service 承担业务校验、权限范围和跨 CRUD 编排。
- CRUD 只负责持久化查询，不把 HTTP 细节传入数据层。
- 通用系统能力放在已有核心模块；招投标运营业务创建独立、语义明确的领域模块，不继续堆入 `module_system`。

## API 与类型

- 路由统一注册到现有 `/api/v1` 体系，使用项目已有响应类和异常处理，不直接返回随意结构的字典。
- 请求和响应使用明确的 Pydantic Schema；不要把 ORM 对象或数据库内部字段未经筛选直接暴露。
- 分页、排序、数据权限、软删除、审计字段沿用现有 BaseCRUD/Schema 约定。
- 保持异步调用链；数据库、Redis、HTTP 或文件 I/O 不得在 async 路由中使用阻塞实现。
- 新增状态值优先定义枚举或统一常量，避免控制器、服务和前端各自维护魔法数字。
- 日期时间写 ORM 时使用 Python 原生类型，JSON/Redis 序列化遵守现有 `model_dump(mode="python"|"json")` 约定。
- 认证、刷新令牌、当前用户、头像/文件 URL 和公共响应包络被桌面端使用。修改时保持兼容，或在同一任务中完成调用方迁移。

## 权限、安全与日志

- 每个非公开接口都必须使用现有认证和权限依赖；前端权限控制不能替代后端鉴权。
- 运营人员属于单个“喻信运营团队”，客户端业务则按 `client_app` 隔离。应用级表必须含 `app_id`，查询和写入只能使用令牌中的当前 `app_id`；禁止接受请求参数作为授权范围，超级管理员在应用业务页也不能绕过范围。
- 运营令牌、客户端用户令牌和模型运行令牌必须区分主体类型。客户端最终用户使用独立的 `client_user`，不得复用 `sys_user`。
- 登录验证码按产品要求关闭；不要在单个接口中绕开统一配置实现另一套验证码逻辑。
- 密码使用现有哈希流程，令牌和密钥不得写日志；日志记录业务定位所需上下文，但不记录密码、完整 Token、数据库连接串或个人敏感数据。
- 文件上传继续使用现有校验、存储和静态路由；不得信任客户端文件名、扩展名或路径。
- Redis key 使用稳定命名空间，并为临时数据设置合理 TTL；不要使用全库扫描作为业务查询。

## 数据库与迁移

- ORM 模型变更必须生成并审查 Alembic 迁移；迁移文件和模型代码在同一提交中交付。
- 迁移应可向已有数据安全执行。新增非空字段时提供默认值、回填或分阶段迁移方案。
- 不编辑已在线上执行过的历史迁移来伪装新变更，应新增迁移。
- 初始化脚本必须幂等，默认组织名称使用“喻信运营团队”，默认客户端仅创建真实业务所需的 `bid_agent`，不要创建额外演示组织、客户端或用户。
- 测试或迁移前确认 `ENVIRONMENT` 和数据库目标。未经用户明确授权，不对 dev/prod 远程数据库执行清库、重建、批量修复或手写数据变更。
- 并发更新、余额/配额、任务状态等关键写入需要事务和冲突策略，不能依赖前端避免重复提交。

## 配置与部署边界

- 配置字段集中在 `app/config/setting.py`，本地环境值放在 `env/.env.*`，Docker 生产环境由服务器 `docker/.env.backend` 统一注入；不要在业务代码硬编码主机、端口、密码或线上 IP。
- 新增配置项时提供类型、合理默认值、校验和 `.env.example` 说明。
- 线上后端通过 Docker 运行，并连接共享 PostgreSQL、Redis、Nginx 网络。部署改动不得重建、停止或改名共享容器。
- 健康检查必须保持轻量，不在探针中执行迁移、外部写入或高成本查询。

## 测试与质量

- 修复缺陷时先补能复现问题的测试；新增业务至少覆盖成功、权限/非法输入和关键边界。
- API 测试复用 `tests/conftest.py` 的测试环境，不连接真实 dev/prod 数据库和 Redis。
- 测试断言关注公开行为和响应契约，避免紧耦合无关实现细节。
- Ruff 配置以 `pyproject.toml` 为准，不手工制造另一套格式规则。

在 `backend/` 下按改动范围执行：

```powershell
uv run ruff check <改动文件或目录>
uv run ruff format --check <改动文件或目录>
uv run pytest <相关测试文件> -q
```

交付前在条件允许时执行：

```powershell
uv run ruff check .
uv run pytest -q
```

- 失败时说明是本次回归还是仓库既有问题，不能删除测试或降低断言来获得通过。
- 只改文档时不要求启动数据库，但仍需检查命令、路径和 `git diff --check`。
