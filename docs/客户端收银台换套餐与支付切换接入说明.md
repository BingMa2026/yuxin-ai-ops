# 客户端收银台：换套餐、换支付方式与未支付订单

更新：2026-10-19。适用于调用喻信运营端的所有客户端应用；本文可直接发给客户端接入方。

## 交互规则

待支付订单按订单管理，不锁住用户的整个购买入口。用户可以先不付款，稍后从订单记录中继续支付；有效付款码以 `expires_at` 为准，过期后重新核验并创建购买。订单实际收款、权益发放、渠道是否关单分别判断。

| 用户操作 | 接入方式 |
| --- | --- |
| 同一次请求超时、断网后重试 | 保留原套餐、渠道、参数和 `idempotency_key`，重复 POST 恢复同一订单 |
| 同一次购买换套餐、换微信/支付宝 | 新幂等键 + `replaces_order_no=当前订单号`，创建关联的新订单，无须等旧单关单成功 |
| 明确再买一份独立商品/订阅 | 新幂等键，不传 `replaces_order_no`；普通未支付单不阻止下单 |
| 稍后付款 | 从本人订单记录找回原单；GET 后只展示仍有效、尚未被替换的付款码 |
| 取消当前订单 | 调取消接口；200/closed 才显示已取消，202 继续核验；仍可关联更换购买 |
| 从积分模式换成时长模式，或反向切换 | 按应用允许模式预览，保留 `mode_version`，需要重置旧权益时让用户明确确认，再创建订单 |

当前支付订单同时承载套餐报价与单一渠道交易，因此切换渠道会产生新的支付订单号。客户端用替换关系表示同一次收银台选择，不能将换渠道视为退款或在旧单上修改渠道。

## 创建与更换订单

所有地址以 `/api/v1` 为前缀，使用本人客户端 Bearer Token。服务端从 Token 取得用户和应用，不接受客户端指定其他用户或应用。金额均为整数分。

原订单 A 已创建但未支付。用户改选套餐 202，并使用支付宝：

```http
POST /api/v1/client/payment/orders
Authorization: Bearer <client_access_token>
Content-Type: application/json

{
  "catalog_plan_id": 202,
  "provider": "alipay",
  "idempotency_key": "checkout:20261019:unique-new-attempt",
  "auto_renew": false,
  "replaces_order_no": "YX20261019030000EXAMPLE001"
}
```

协议场景要求确认时同时传现有 `agreement_acceptance`；跨模式需要重置确认时同时传现有 `mode_switch_confirmation`。同键重试必须保留完整原请求，不更换套餐、渠道、替换来源或模式确认版本。

成功通常为 HTTP 201，包络仍为 `{code,msg,data,status_code,success}`。下列仅展示关键订单字段，实际 `data` 是完整 `PaymentOrderOut`：

```json
{
  "code": 0,
  "success": true,
  "status_code": 201,
  "msg": "订单创建成功",
  "data": {
    "order_no": "YX20261019030100EXAMPLE002",
    "catalog_plan_id": 202,
    "provider": "alipay",
    "amount_fen": 190,
    "status": "pending",
    "pay_url": "https://qr.alipay.com/EXAMPLE_ONLY",
    "replaces_order_no": "YX20261019030000EXAMPLE001",
    "replaced_by_order_no": null
  }
}
```

新订单建立且不是明确的 `failed` 后，原订单 A 的 `replaced_by_order_no` 指向 B，`pay_url=null`，后台持久化关闭意图并安排查单/关单。客户端立即展示 B，允许继续选择其他套餐/渠道。关系字段不是新的支付状态：A 可能暂时仍是 `pending/confirming`，B 可以正常付款。只展示当前 B 的付款码，提醒用户不要付款旧码。

新下单明确 `failed` 时不撤下原单。失败订单 B 仍会保留请求的 `replaces_order_no=A` 用于核验；再次更换应关联 A，不能误以为 B 已替换 A。GET A 可确认它是否已有 `replaced_by_order_no`。新下单为 `confirming` 时结果未知，新单仍承接这次购买，原单安排关单；先保存新单，允许继续关联更换，不能伪造付款码。

| 结果 | 接入方处理 |
| --- | --- |
| 201 / `pending` | 展示新订单与有效付款码；查询新单 |
| 202、`success=false`、含 `confirming` 订单 | 从错误包络恢复完整新单；保留新号和幂等键，可查单/取消/关联更换 |
| 502、`success=false`、含 `failed` 订单 | 保存失败记录，原单保持可用；换购时重新确认原单的替换关系 |
| 404 | 原单不存在、已删除或不属于本人/本应用；不泄露其他用户记录 |
| 409 原单已收款 | GET 原单、刷新权益；需要再次购买时创建明确的独立新购买 |
| 409 原单已被更换 | GET 原单，通过 `replaced_by_order_no` 查询最新订单；不要换键反复替换旧来源 |
| 409 同键参数变化 | 恢复原请求；真正更换套餐/渠道时生成新键并显式关联 |
| 网络超时且没有订单号 | 保留原请求和原键，先重试恢复订单号，再关联更换；禁止丢键连续建未知订单 |

## 模式切换

读取 `GET /api/v1/client/runtime-config?schema_version=2`，只展示 `allowed_billing_modes` 允许的模式。用户选择目标套餐后调用现有接口：

```http
POST /api/v1/client/billing/mode-switch/preview
Content-Type: application/json

{
  "catalog_plan_id": 202,
  "target_mode": "duration",
  "expected_mode_version": 3
}
```

普通 `created/pending/confirming` 订单不再导致预览 `can_switch=false`。当 `requires_reset_confirmation=true` 时，应展示 `reset_summary` 中将失效的全部剩余权益，让用户确认，然后在新订单中附上：

```json
{
  "mode_switch_confirmation": {
    "expected_mode_version": 3,
    "accept_reset": true
  }
}
```

模型调用预占、待处理退款、模式版本过期、应用不允许该模式或未被替换且已收款待履约的订单，仍可能拒绝切换。此类错误按返回原因处理；不按“账号存在任意订单”统一禁用整个购买入口。自备模型/时长模式与含模型费用/积分模式的实际任务权限仍由运行时授权决定。

## 旧单后来付款、重复付款与权益

- 未被替换的独立原订单仍按原报价和当前授权核验付款；不根据本地页面关闭与否丢弃收款。正常同套餐续期、时长累计、积分包发放沿用现有规则。
- 已被替换的旧订单收到验签付款时，保留 `paid/paid_at/provider_trade_no`，写入 `mode_switch.status=requires_confirmation` 和说明，进入财务核对/退款；不再次发权益或切回旧模式。被替换旧单的此类核对不锁住新订单购买。
- 独立旧套餐付款前若已购买其他同等级或更高等级积分订阅，旧款也保留，交财务核对；不自动覆盖当前更高等级订阅。跨模式版本变化的迟到付款同样交财务处理。
- 重复回调/查单保持幂等；退款由运营流程处理，切换渠道不自动退款。付款成功、权益待财务核对时，客户端明确显示原因，避免提示用户继续付款。

## 取消、超时与恢复

取消为 `POST /api/v1/client/payment/orders/{order_no}/cancel`，JSON 可省略，或传 `{"reason":"用户取消购买"}`。200/closed 已关闭，202/confirming 继续核验，409 已付款不取消。保留完整错误包络的订单；别将 HTTP 202 当成普通成功。

订单新码有效期 15 分钟。微信/支付宝查单与关单成功后更新为 closed；网络或结果未知时继续核验。支付宝未扫码预下单可能返回交易不存在：具有有效期证据的订单在码过期并留出 1 分钟余量后，经验签查单确认未建单，才能关闭本地订单。替换新单不依赖旧单立即达到 closed。

关闭收银台停止页面轮询，重新打开恢复当前订单；主动查询、再次购买后的权益同步均使用服务端结果。接口响应新增可空 `replaces_order_no/replaced_by_order_no`，原有 `closed_at/cancel_requested_at/failure_reason/mode_switch` 要保留。

## 上线与验收

运营端先备份并应用 `20261019_checkout_replace` 迁移，它仅新增两个可空关联字段，不批量改历史订单、余额或权益。老客户端可继续用原 POST；要获得顺畅换购体验，接入方仍需移除客户端的未支付订单全局锁，并接入上述关联字段。

验收至少覆盖：同请求断网重试不多建单；未付 A 时创建独立 B；A 换套餐/渠道得到 B 且旧码撤下；旧渠道关单异常不挡 B；新下单明确失败保留 A；A、B 先后付款只给当前关联订单发权益、旧款可追溯；旧单被他处更换后能恢复最新单；跨用户/应用不可替换；跨模式保留明确重置确认；取消 202/409 能恢复订单。
