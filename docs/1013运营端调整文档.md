# 1013运营端调整文档

日期：2026-10-13。状态：运营端核心功能已实施并发布；共享数据库已核验处于 `20261013_service_modes`。客户端仍需按新版协议联调。

本次将应用模式改为“含 token 费用、token 自费、均支持”三个单选项，并支持按用户记录当前生效模式。运营页面需要区分应用支持范围、套餐权益类型、用户当前模式及历史订单类型，不能继续用一个应用开关决定所有页面的显示。

## 1. 统一名称与业务含义

### 1.1 应用模式使用三个单选项

应用配置中的原“启用平台模型服务”开关改为“服务模式”单选组。**新建应用默认选中“均支持”（user_choice）**；创建表单、创建接口省略该字段时的默认值及数据库新增记录默认值应保持一致。运营人员可按需改为另外两种模式。

| 显示名称 | 建议内部值 | 对应原功能 | 说明 |
| --- | --- | --- | --- |
| 含 token 费用 | `credits_only` | 平台模型、积分订阅 | 使用平台模型，按原积分及订阅规则使用 |
| token 自费 | `duration_only` | 自配模型、按天订阅 | 用户配置模型地址、Key 和模型名称，供应商费用自行承担，平台收取客户端使用时长费用 |
| 均支持 | `user_choice` | 新增允许用户二选一 | 同一应用可售两类套餐，每个用户同一时间仅一种模式生效 |

“含 token 费用”是原积分模式的名称调整，不代表无限 token、不再扣积分或取消模型权限校验。“token 自费”不代表客户端使用免费，仍需有效时长授权。

“均支持”不是第三种套餐权益，也不能作为用户当前模式。模式选择必须是单选，不能使用两个可独立开关的复选项。

默认值仅用于新建应用，不批量覆盖已有应用配置。用户仍按自己的当前生效模式使用；新用户尚未选择或开通时显示“未选择”，不能因应用默认均支持而同时放行两条计费路径。读取配置失败或遇到旧字段缺失时，也不能擅自按均支持放行。

### 1.2 分开应用配置与权益类型

| 概念 | 值 | 用途 |
| --- | --- | --- |
| 应用服务模式 `service_mode` | credits_only / duration_only / user_choice | 决定当前应用允许销售和使用的范围 |
| 套餐、订阅权益类型 `entitlement_kind` | credits / duration | 决定每条记录发积分还是增加天数 |
| 用户当前模式 `active_billing_mode` | credits / duration / null | 决定用户此刻走哪条授权和模型调用流程 |
| 订单权益类型 | 下单快照中的 entitlement_kind | 解释历史交易，不受应用后来改名或切换影响 |

运营页面中，credits 统一显示“含 token 费用”，duration 统一显示“token 自费”。底层积分、天数和计费规则保持各自语义，不把两个权益类型也改成三个。

## 2. 当前问题与改动范围

核对当前实现发现：

- 产品刊例的“权益周期”读取 benefit_period_days；相邻“计费权益”在 duration 行也读取 benefit_period_days，造成截图中的“90 天 / 90 天”。这是该表格的显示逻辑问题，不是两份独立的时长权益。
- 后端已有时长套餐校验：订阅类型、积分为 0、积分释放计划为空。页面应如实显示这些字段，不能用天数替换积分。
- 产品刊例的默认类型和模板筛选、价格策略候选套餐、订阅列表积分列、用户详情等仍依赖应用的 platform_model_enabled 布尔值。
- 现有订阅记录按应用和用户唯一，适合保留“当前生效订阅”语义，但还缺少独立的用户模式及完整切换记录。
- 下单、支付到账、积分调整、调天数和部分奖励逻辑仍按应用布尔开关判断，需要支持“应用允许范围＋用户当前模式”。

因此，本次既有名称和页面调整，也有服务端契约及权益处理调整。不能仅替换三个文案或只修改下拉选项。

## 3. 运营页面如何按类型展示

页面按用途选择分组方式，不要求把所有页面拆成两个独立菜单。

| 页面 | 建议展示方式 | 判断依据及调整点 |
| --- | --- | --- |
| 客户端管理 | 三个单选项及当前模式标签 | 应用 service_mode；展示名称和修改确认统一 |
| 产品刊例 | “含 token 费用 / token 自费”分组标签，提供全部查看 | 按套餐 entitlement_kind 分组；均支持可管理两组在售产品 |
| 价格标准与模板 | 类型筛选及模板类型标签，编辑时明确类型 | 按模板类型决定字段；不让同一模板同时包含两类权益 |
| 价格策略 | 按类型筛选候选套餐，明细保留类型标签 | 由每条套餐决定定价和校验规则，不能按全局应用开关过滤掉另一类 |
| 订阅管理 | 同一列表增加类型筛选及类型列，支持全部查看 | 每条订阅的 entitlement_kind，按行显示积分或期限 |
| 用户管理列表 | 保持原列表，不新增模式列、模式筛选或切换状态 | 本次模式展示仅放在用户详情 |
| 用户详情 | 增加“当前使用模式”一项，原权益和历史信息保持原有入口 | 读取用户 active_billing_mode，仅显示一种当前模式 |
| 订单与财务 | 同一账簿按订单权益类型筛选，增加切换处理状态 | 下单快照决定类型；支付状态与切换状态分别展示 |
| 退款 | 按订单类型显示权益影响 | 积分订单显示积分回收；时长订单显示时长终止和到期变化 |
| 模型服务与平台用量 | 应用允许含 token 费用时可配置平台模型 | 实际调用还校验用户当前模式；保留历史调用和费用记录 |
| 活动奖励与积分转赠 | 增加适用权益类型或明确积分适用条件 | 新积分发放按接收用户模式及活动规则判断，不能因应用均支持而无差别发放 |
| 统计和导出 | 增加类型维度，金额可汇总，权益数量分开 | 积分与天数不能相加或放进同一数值指标排序 |

单一模式下可默认进入对应类型，但管理端应保留查看另一类型历史、草稿或下架资料的能力。客户端可售列表仍由应用允许范围、刊例状态和用户资格限制。

类型筛选应由接口执行，并与分页、排序、统计和导出保持一致，不只过滤当前页数据。所有查询继续限制在当前 app_id，不增加跨客户端的“全部客户端”入口。

## 4. 产品刊例的具体调整

### 4.1 修正截图中的列含义

固定列名和单位，不再根据应用模式把积分列改成天数列：

| 列 | 数据来源 | 含 token 费用 | token 自费 |
| --- | --- | --- | --- |
| 类型 | entitlement_kind | 含 token 费用 | token 自费 |
| 权益周期 | benefit_period_days | 保留原套餐周期含义 | 实际购买的使用天数，如 90 天 |
| 积分（计费权益） | total_credits | 实际积分数量，如 100,000 积分 | 0 积分 |
| 积分有效期 | credit_valid_days | 按原规则显示 | 不适用，不显示成订阅天数 |
| 释放计划 | release_plan | 按原规则显示 | 无积分释放计划 |

示例：

| 套餐 | 类型 | 权益周期 | 积分（计费权益） |
| --- | --- | --- | --- |
| 示例积分订阅 | 含 token 费用 | 30 天 | 100,000 积分 |
| 示例时长订阅 | token 自费 | 90 天 | 0 积分 |

时长套餐的 total_credits 应在数据上也是 0，不是仅在前端强行显示 0。如果发现存量 duration 记录积分非零，应标识异常并核查，不能通过显示层掩盖错误数据。

这里的 0 是**该时长套餐发放的积分**。不能据此把用户历史真实积分账户余额或历史订单积分改成 0；历史权益是否失效，必须通过明确的切换处理记录。

### 4.2 新建和编辑刊例

- 均支持应用新建套餐时，必须选择“含 token 费用”或“token 自费”；单一模式默认并限制为允许类型。
- 选择模板后继承明确的权益类型，只允许使用匹配类型的模板。
- token 自费固定为订阅套餐，权益周期为 1–3650 的整数天，积分固定为 0，释放计划为空，沿用有效正价格及手动续费规则。
- 含 token 费用保留原积分订阅、积分包、积分释放及价格约束，不将新增的时长规则套到所有产品上。
- 已有刊例尤其已有销售记录时，不直接改变其 entitlement_kind；需要另一类型产品时新建刊例，保留旧订单快照。
- 发布、上架、批量操作与复制套餐均需校验应用允许范围，不能只在表单中限制。
- 排序时，“权益周期”按天数排序，“积分（计费权益）”按积分数排序，不使用格式化字符串比较。

## 5. 价格标准和策略调整

价格标准、模板和客户端刊例应贯通同一个权益类型，复制、预览、发布及版本回退不能丢失 entitlement_kind。

| 项目 | 含 token 费用 | token 自费 |
| --- | --- | --- |
| 套餐权益输入 | 原积分数量、周期、释放方式 | 使用天数，积分固定 0 |
| 模型成本相关规则 | 保留原模型成本及积分测算 | 不套用平台代付 token 的积分成本测算 |
| 价格策略候选 | 允许的 credits 刊例 | 允许的 duration 刊例 |
| 价格预览 | 价格＋积分权益 | 价格＋使用天数＋0 积分 |

均支持时两类刊例均可参与各自适用的策略，不能因应用不再是原布尔值就漏掉一类。价格策略可以沿用原结构，但每条明细按自身类型计算；若现有策略存在整组统一的积分成本假设，应按类型拆组，不跨类型套用。

token 自费不等于运营成本为零。这里只是不替用户承担供应商 token 费用，其他成本指标如需统计，保持独立定义。

## 6. 用户当前模式与订阅记录

### 6.1 仅在用户详情显示当前模式

用户管理列表保持原样，不新增模式列、模式筛选、切换状态或模式摘要。用户详情只增加“当前使用模式”一项：

| 用户当前状态 | 详情显示 |
| --- | --- |
| active_billing_mode=credits | 含 token 费用 |
| active_billing_mode=duration | token 自费 |
| 尚未选择或开通，active_billing_mode=null | 未选择 |

用户同一时间最多只有一种生效模式。“均支持”仅表示应用允许用户选择两种模式，不能显示为用户当前模式，也不能把两种模式同时标记为生效。未选择是尚无生效模式，不是第三种用户模式。

切换未完成时仍显示原生效模式；切换成功后刷新为目标模式。服务端保留切换审计记录，相关支付及切换处理状态由订单、财务页面核验，不要求在用户详情另增模式变更记录模块。

### 6.2 调积分与调天数

- 操作入口结合用户当前模式、应用允许范围和运营人员权限决定，不能只检查应用是否支持某一种模式。
- 含 token 费用用户按原权限调整积分；token 自费用户按调天数权限调整期限。
- 调整权益不隐式切换用户模式，也不自动解除账号停用或订阅取消。
- 未选择模式的用户如需人工开通，必须明确目标模式并走服务端统一开通流程；不能靠第一次调积分或调天数悄悄决定模式。
- 如后续允许运营人员人工协助切换，需独立权限、原因和影响确认，调用同一切换处理流程，不能通过两次普通调整模拟切换。

### 6.3 订阅及权益周期

订阅管理按每条订阅的类型显示，不按应用全局开关统一隐藏列。全部视图至少展示类型、用户、套餐、起止时间及状态；积分和剩余时长分列或按类型标签切换。

刊例的“权益周期”是一次购买约定天数；用户当前到期时间和剩余时间则由实际发放、续期、退款及人工调整后的权益记录决定。两者不能混为一谈。

现有每应用每用户唯一订阅记录可继续作为当前订阅，但历史周期要保留类型和来源快照。切换更新当前订阅时，不能把历史积分周期解释成天数，也不能由旧周期重新计算出已经终止的权益。

## 7. 支付和模式切换的服务端配套

### 7.1 下单校验

下单从只检查应用布尔开关，调整为检查：应用允许类型、目标套餐类型、用户当前模式和是否完成切换确认。

同模式订单保持原续期或充值流程。跨模式购买先实时查询剩余积分或天数，弹窗提醒并由用户点击确认；不保存预览记录、确认编号或确认快照。订单只保留切换标记和处理结果，服务端自行计算实际重置量。

### 7.2 支付后生效

建议沿用客户端方案：支付成功且最终校验通过后，再终止旧模式全部剩余权益、发放新权益并更新当前模式。

- 选择套餐、生成预览、创建订单不清理旧权益。
- 预占积分、进行中的调用或退款应先结算，或明确阻止切换。
- 提醒数值是查询时的剩余量，实际重置以支付成功、切换生效时的全部剩余量为准；提示中必须说明该规则。新增赠送积分或人工增加天数也属于旧模式剩余权益。
- 旧权益终止、新权益发放、用户模式更新与审计写入需要事务一致性。
- 同一订单重复回调、补单或重复操作只执行一次，使用应用和用户范围内的并发控制。
- 旧订单延迟付款不得自动覆盖更新的用户模式；财务页面展示已付款但权益待处理状态。

服务端预览和执行复用同一权益口径。积分可用、待释放、预占、时长周期必须分别处理，不能仅修改账户余额或 subscription.current_period_end。

## 8. 财务 退款和统计展示

订单列表新增权益类型及模式切换状态，保留统一财务账簿。“支付成功”与“权益发放完成／模式切换完成”是不同维度，不能用一个状态覆盖。

| 场景 | 运营页面及处理要求 |
| --- | --- |
| 含 token 费用订单 | 按原快照展示积分发放、消耗、回收等 |
| token 自费订单 | 展示购买天数、权益起止和剩余可处理时长；套餐积分为 0 |
| 已付款但切换未完成 | 提供待处理筛选、原因及关联切换记录 |
| 退款预览 | 按订单原类型计算影响，不能根据用户现模式决定回收哪种权益 |
| 已被切换终止的旧权益 | 显示已处理来源，不能在退款时再次扣减或恢复 |
| 撤销或失败的切换 | 明确资金与权益状态，不直接回滚成旧模式并复活已消费权益 |
| 统计和导出 | 订单金额可合并统计，积分、天数和 token 用量分开统计 |

不能把“token 自费”的套餐积分 0 解释成用户供应商没有 token 消耗。平台无法掌握的供应商费用不统计为已确认的 0 元平台成本。

## 9. 数据及接口调整建议

以下为建议契约，实际名称与客户端文档联调后确定。

| 对象 | 建议新增或调整 | 用途 |
| --- | --- | --- |
| 客户端应用 | service_mode，沿用策略版本并发校验 | 保存三种单选模式 |
| 用户模式记录 | app_id、user_id、active_billing_mode、mode_version、生效时间 | 唯一权威来源，不以最后订单推断 |
| 套餐及模板 | 保留 entitlement_kind 两值，类型筛选和后端校验支持允许集合 | 无须创建第三种权益类型 |
| 订阅与权益周期 | 当前类型与历史快照分离，记录失效来源及处理结果 | 防止切换、退款和重新计算相互覆盖 |
| 支付订单 | 保留是否允许重置的标记和切换处理结果，不关联独立确认记录 | 原支付状态继续表示资金结果 |
| 用户详情响应 | 增加 active_billing_mode | 仅用于详情的当前使用模式展示，不为本次需求增加列表模式字段或筛选 |
| 运行配置响应 | service_mode、allowed_billing_modes、active_billing_mode、mode_version | 客户端区分应用范围与用户选择 |
| 刊例 订阅 订单查询 | 增加一致的类型筛选和统计维度 | 分组、分页、导出一致 |

旧 `platform_model_enabled` 只能表达两种状态，不能承载“均支持”。新增契约需版本化，兼容窗口内也不能让旧客户端把两个互斥布尔值同时为 true 当作有效策略。

平台推理和语音鉴权、积分发放和转赠、调天数、套餐上架、价格发布和支付到账等服务端入口，应分别检查应用允许范围、对象权益类型和用户模式。公共校验不可简单改成“均支持就全部放行”。

## 10. 应用模式变更与历史数据

| 应用变更 | 建议规则 |
| --- | --- |
| 含 token 费用 → 均支持 | 保留已有用户模式及权益，允许新增 token 自费套餐销售 |
| token 自费 → 均支持 | 保留已有用户模式及权益，允许新增含 token 费用套餐销售 |
| 均支持 → 任一单一模式 | 先核验不匹配用户权益、进行中订单和切换；有未处理权益时阻止直接变更 |
| 两个单一模式互相切换 | 保留原权益承接校验，不能通过改应用配置批量清空用户权益 |

限制销售范围时，不匹配产品可下架，历史产品和订单仍可查询；扩大范围不自动上架未经确认的草稿产品。

存量迁移建议：原 true 映射 credits_only，原 false 映射 duration_only；已有用户当前模式按原有效配置与订阅核对后初始化，有矛盾记录需单独处理。不能把所有用户初始化成未选择，也不能利用这次迁移清空历史余额。

新字段、约束和索引通过正式数据库迁移交付，先部署兼容服务，再完成页面与客户端版本联调，最后开放均支持。文档中的方案不能代替实际数据库版本检查。

## 11. 已确认规则及验收

名称和显示口径已明确：应用三个单选项使用“含 token 费用、token 自费、均支持”；token 自费刊例的权益周期显示实际天数，积分（计费权益）为 0。

已确认：切换时重置旧模式全部剩余权益，包含积分包、活动赠送及人工增加的天数，弹窗展示剩余积分或天数并由用户点击确认，不另建确认记录。按购买目标模式订阅实现，不提供绕过购买直接切换的入口。新增权益按生效时的剩余量重置；已付款后出现预占、退款或模式版本变化时进入待核对；首版通过财务核对／退款处理，不提供免确认强制清理接口。退款不自动恢复被用户确认重置的旧权益，也不自动改回旧模式。

验收重点：

- 新建应用默认选中均支持，创建接口及数据库默认值一致；已有应用原配置不被覆盖。三种应用配置均可正确保存和读取，旧两种模式行为不回归。
- 同一均支持应用内，产品刊例两类可分别管理、筛选、发布和导出。
- 90 天的 token 自费刊例显示“权益周期 90 天、积分（计费权益）0 积分”，不再重复两列天数。
- 时长套餐数据为零积分、无释放计划；异常历史数据不会被页面强制归零掩盖。
- 用户详情只显示一种当前使用模式；用户列表不新增模式列、筛选或切换状态。订阅按各自类型展示，调积分与调天数权限正确。
- 价格模板、策略、刊例类型一致，另一类型产品不会因全局开关被错误过滤。
- 切换确认、付款、权益发放及模式记录一致；重复通知不重复执行。
- 预览后权益变化、迟到订单、退款、并发切换均不破坏余额与期限。
- 历史订单与退款始终使用原快照，不随应用或用户新模式改写。
- 表格、详情、统计和导出使用同一类型及单位口径；浅色、深色和窄窗口显示可用。

- `GET /api/v1/client/runtime-config?schema_version=2` 返回新版完整字段；不传参数仍按 v1。均支持应用请求 v1 会提示升级，不以双开关同时开启代替模式选择。
- `POST /api/v1/client/billing/mode-switch/preview` 请求包含 `target_mode`、`catalog_plan_id`、`expected_mode_version`。实时计算、不持久化预览；响应包含模式及策略版本、`can_switch`、`blocked_reason`、`requires_reset_confirmation` 和 `reset_summary`。

- 同模式续费沿用原逻辑。跨模式付款核验后，在同一事务内失效旧模式全部剩余权益、发放目标权益、更新模式版本和审计；事务失败整体回滚。重复回调和迟到订单不会重复发放或切回旧模式。
