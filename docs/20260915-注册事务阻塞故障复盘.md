# 注册失败导致连接池耗尽：2026-09-15 排查与修复

## 现场与触发范围

生产版本为 `25909243`。2026-09-14 16:47:19（北京时间）启动的注册事务持有 `client_app` 行锁，最后查询 `client_user` 是否已有该账号；另一会话等待插入 `client_auth_event`。二者均来自运营后端容器。

接口为 `POST /api/v1/client/auth/register`。主会话为 `idle in transaction`，失败日志会话等待主会话的 transactionid；后续客户端行锁、外键检查和默认客户端更新持续排队。最终 30 个应用连接被占满，健康检查、当前用户接口和定时任务出现 QueuePool 超时。现场 CPU 基本空闲、可用内存约 7.8 GB，没有发现 OOM。

失败日志在等待中未能提交，因此不能从现有证据确认原请求是重复账号还是密码强度校验失败，也无法恢复确切的 HTTP 请求 ID。主事务最后的 SQL 将触发范围定位到账号存在性查询之后、创建用户之前的注册失败路径；重复账号可用于确定性复现。

## 根因

协议验证通过 `lock_app(... FOR UPDATE)` 保持场景配置与接受记录的一致性。注册校验失败后，旧实现仍持有该事务，却同步等待另一连接提交失败日志。日志的 `app_id` 外键需要检查被锁的客户端记录：原事务等日志、日志等原事务释放锁，形成跨应用协程与数据库的相互等待。

这不是 PostgreSQL 单独能检测到的纯数据库事务死锁环；现场 lock_timeout、statement_timeout、idle_in_transaction_session_timeout 都为 0，因此可一直等待。增加连接数不能解决根因。

## 修复与防护

1. 先冻结失败日志字段，再回滚失败业务事务、释放锁，最后独立提交失败日志。注册与登录失败共用此路径，成功事务保持原子性。
2. 独立审计最多等待 5 秒，失败记录写入异常输出不含个人信息的服务错误日志，不覆盖原认证错误。
3. 仅运营端 PostgreSQL 异步连接设置：锁等待 5000ms、单 SQL 60000ms、空闲事务 120000ms。对应配置为 `DATABASE_LOCK_TIMEOUT_MS`、`DATABASE_STATEMENT_TIMEOUT_MS`、`DATABASE_IDLE_TRANSACTION_TIMEOUT_MS`。不修改共享 PostgreSQL 配置、不限制同步 Alembic 迁移连接。外部模型请求耗时不等于单 SQL 执行时限。
4. 就绪探针的数据库检查最多等待 3 秒，故障时及时返回 503，不拖满容器探针的 10 秒时限。

## 验证与恢复

- 先保留数据库活动、阻塞链与日志证据，再只重启运营后端，原事务回滚，连接池及访问恢复。共享 PostgreSQL、Redis、Nginx 和其他业务容器没有重启。
- SQLite 回归验证业务写入回滚、失败日志独立留存、审计存储异常时保留原 401，以及协议校验和注册正常路径。
- 独立 PostgreSQL 16 测试库 `auth_lock_regression` 复现注册协议锁加重复账号路径：请求必须在 3 秒内返回原业务错误、失败日志存在、下一请求能立即取得同一行锁，并核对三个会话超时配置。
- 就绪探针使用模拟阻塞检查验证超时和会话释放。

部署后观察应用健康、超过 5 秒的锁等待、连接池超时和审计写入失败；这些保护不能承诺消除所有性能问题，但能避免本次异常无限占用连接。
