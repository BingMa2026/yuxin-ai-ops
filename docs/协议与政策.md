# 协议与政策

入口：用户运营 → 协议与政策。协议列表和使用场景沿用财务中心的搜索区、表格工具栏、列设置、分页和操作列。所有管理接口以运营令牌中的当前 `app_id` 为范围，包括超级管理员；公开接口以客户端稳定编码查找已启用客户端，仅返回已发布正文。

## 维护流程

`bid_agent` 的首批正式正文保存在 `backend/legal/`：用户服务协议、隐私政策、订阅与积分服务协议。部署并完成本项目数据库备份后，在后端容器 `/home` 目录执行 `python -m tools.publish_bid_agent_agreements --apply`，一次性发布 V1、配置 `auth`、`membership_purchase`、`credit_purchase`、`about` 四个场景，并归档旧的 `cs` 占位协议。脚本可重复执行，遇到运营人员修改过的内容会停止而非覆盖。后续内容更新应通过运营端的草稿、预览和发布流程生成新版本；正文涉及法律义务，运营方应复核。

1. 新增协议，填写名称、稳定标识和富文本正文。名称和标识有效后自动保存草稿；失败时保留输入并提示重试。
2. 正文支持标题、强调、列表、链接和表格；服务端使用 HTML 白名单清洗，统一排版。编辑和公开阅读都不接受脚本、事件属性、媒体或任意样式。
3. 填写更新说明，预览后发布。发布立即生效，系统生成 V1、V2 等版本。保存草稿不会替换线上版本。
4. 历史版本只读。恢复旧内容会生成草稿，必须再次发布才生效。两人编辑通过 `revision` 检测冲突，返回 409，不覆盖他人修改。
5. 未发布且未引用的草稿可软删除；发布过的协议归档并保留历史。恢复归档后需重新发布。已使用的稳定标识保留，软删除后不能重用。
6. 在使用场景中选择当前客户端已发布协议，调整展示顺序，保存后立即生效。新增场景需要客户端接入标识；已有场景标识不能修改。

## 使用场景与调用职责

客户端决定展示入口与交互，运营配置场景包含的协议及顺序。支持按协议标识直接读取，或者按场景获取整组协议。场景只允许绑定同客户端已发布协议，被引用协议不能归档或删除。

| 场景标识 | 本次接入位置 | 确认规则 |
| --- | --- | --- |
| `auth` | 客户端登录页阅读、注册确认 | 注册必须同意，服务端校验 |
| `membership_purchase` | 两个订阅购买入口 | 必须同意，服务端根据商品类型选择场景 |
| `credit_purchase` | 两个积分包购买入口 | 必须同意，服务端根据商品类型选择场景 |
| `about` | 客户端设置 → 常规 → 协议与政策 | 阅读入口 |

登录页提供 `auth` 场景的协议阅读入口，注册表单要求主动确认。登录本身不强制老用户再次同意，不默认每次正文更新都拦截老用户登录。注册、购买场景一旦配置，不允许删除或关闭确认要求；可以替换关联协议。

## API

以下路径均位于 `/api/v1` 下，沿用标准响应 `{code,msg,data,status_code,success}`。

### 运营接口

- `GET/POST /operations/agreements`：分页查询/新增草稿。
- `GET/PUT/DELETE /operations/agreements/{id}`：详情/保存草稿/删除未发布协议。
- `POST /operations/agreements/{id}/publish|archive|unarchive`：发布、归档、恢复。
- `GET /operations/agreements/{id}/versions`：发布历史。
- `POST /operations/agreements/{id}/versions/{version_id}/restore`：复制历史正文为草稿。
- `GET/POST /operations/agreements/scenes`：场景分页查询/创建。
- `PUT/DELETE /operations/agreements/scenes/{id}`：更新/删除场景。
- `GET /operations/agreements/acceptances`：分页查询同意记录，可按 `user_id` 筛选。

协议查询参数：`page_no`、`page_size`、`keyword`、`status`、`has_draft`。场景查询使用分页和 `keyword`。修改、发布、恢复、归档携带当前 `revision`；删除在查询参数中携带 `revision`。

权限前缀 `workspace:user:agreement:`：`list`（查看）、`update`（新增编辑）、`publish`（发布归档）、`delete`（删除）、`scene`（配置场景）。迁移不会向既有普通角色自动授予新写权限。

### 客户端公开读取

- `GET /public/client-apps/{app_code}/agreements/{code}`
- `GET /public/client-apps/{app_code}/agreement-scenes/{code}`

公开读取不要求登录，返回 `Cache-Control: no-store`。未配置、未发布、归档或停用客户端不会回退到其他客户端内容。场景响应的 `data` 示例：

```json
{
  "code": "auth",
  "name": "登录注册",
  "revision": 1,
  "require_acceptance": true,
  "agreements": [
    {
      "code": "user_agreement",
      "version_id": 12,
      "version": 2,
      "title": "用户协议",
      "content": "<p>协议正文</p>",
      "published_at": "2026-09-11T09:00:00Z"
    }
  ]
}
```

`agreements` 的顺序即展示顺序。直接读取返回其中一项的结构。阅读页展示当前返回的具体正文，不能在用户确认后悄悄换为新版。

### 注册和购买确认

`POST /client/auth/register` 和 `POST /client/payment/orders` 新增可选字段：

```json
{
  "agreement_acceptance": {
    "scene_revision": 1,
    "version_ids": [12, 15]
  }
}
```

场景配置后，服务端要求提交完整且不重复的当前版本 ID 集合及场景修订号，遗漏、跨客户端或过期版本返回 409。前端清除勾选并重新加载协议，保留注册和购买输入。校验与用户创建/订单创建/记录写入同事务；支付重放返回原订单，不重复记录同意。

记录包括客户端、用户、场景、场景修订号、确切版本 ID、业务关联和时间。它记录用户确认行为，不把“打开阅读页”当成同意。

## 上线顺序与兼容

1. 部署后端并执行 Alembic `20260911_agreements`，部署运营前端。
2. 为每个客户端维护真实协议正文并发布；按需配置使用场景。
3. 发布接入协议的新客户端。新客户端在必需场景未配置或加载失败时明确提示、禁止继续注册/下单。

为兼容存量客户端，在某个必需场景从未配置且请求未提交确认字段时，后端保持原有流程；运营首次配置该场景即启用强校验，旧客户端会收到需确认协议的提示。应协调客户端升级与场景启用窗口。已配置场景不会因删除记录而绕过确认。

迁移只创建协议相关表和管理菜单，不自动生成具有法律含义的协议正文，不向已有用户补写同意记录，也不自动启用注册或购买场景。

如果安装环境已提前通过 ORM 创建协议表，迁移会核验列、类型、空值约束、主键、唯一约束和外键，结构一致时保留原表与数据并补齐索引、菜单；结构不一致则停止，不能直接标记迁移完成。已存在或已删除的协议菜单不会被重复创建或恢复。
