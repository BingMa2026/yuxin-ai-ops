# 本地模型模式与客户端使用天数充值：运营端完整调整方案

- 日期：2026-10-08
- 状态：设计提案，尚未实施；本文不代表已完成迁移、测试或上线。
- 适用项目：`D:/2026/python/yyd`
- 配套方案：[客户端完整调整方案](../../bid-agent/bid-agent-client/docs/本地模型与按天充值-客户端调整方案.md)
- 依据：本次需求确认及两个仓库的现有代码。接口、新字段、新文件均为建议设计。

## 1. 已确认需求与建议边界

### 1.1 已确认

1. 运营端在“客户端管理 → 基本资料”增加配置，控制当前客户端是否使用用户自行配置的模型。
2. 客户端登录后获取该配置；本地模式下用户自行配置模型地址、Key。
3. 本地模式不要求套餐配置平台模型额度或积分。
4. 本地模式充值购买的是客户端使用天数，不是积分。

### 1.2 本方案建议，尚不等于用户确认

- 一个客户端应用同一时刻使用一种模式：platform 为平台模型＋现有积分规则；local 为用户自配模型＋时长授权。不在第一版引入混合计费。
- 界面可用“启用本地模型”开关，旁注明“用户自行配置模型地址和 Key，充值增加客户端使用天数”。这里“本地”指连接配置与请求发起在客户端，不要求推理服务器在本机。
- 使用天数为连续自然流逝的时长，1 天按 24 小时计算，不按启动天数或登录次数扣减。
- 第一版时长套餐提供同一组客户端功能，仅价格、天数、说明不同，不引入等级升级折算。后续若需要功能分级再单独扩展。
- 第一版不自动扣款；零元时长不开放无限自助领取；赠送天数走审计完整的运营入口。
- 第一版采用在线授权与短时内存缓存，不承诺长期离线可用。
- 本地模式只免除平台模型积分，不代表语音、搜索、第三方知识库等收费服务自动免费。

### 1.3 技术审查结论

单独隐藏积分表单会留下后端校验失败、任务被零余额阻断、支付后仍发积分等问题，必须按完整业务链实施。模式配置属于应用，使用期限属于应用下的用户，不能混用。

客户端由用户控制，本地授权校验可以防止普通界面和配置绕过，不能宣称对恶意修改的二进制提供绝对防破解能力。平台凭据和平台计费必须始终在服务器保护。

## 3. 核心业务规则

### 3.1 模式矩阵

| 行为 | platform | local |
| --- | --- | --- |
| 模型配置 | 运营端管理 | 客户端用户配置 |
| 收费商品 | 原订阅、积分包 | 客户端使用天数 |
| 使用检查 | 原平台规则 | 账号有效＋时长有效 |
| 模型计费 | 平台积分预占与结算 | 不经过平台积分链 |
| 到期后 | 原规则 | 允许登录、充值、配置模型、查看与导出已有成果；不允许新的收费任务 |
| 模型故障回退 | 原平台路由策略 | 不自动使用平台模型 |
| 历史资产 | 原逻辑 | 保留账本，不能自动清空或折天数 |

已有成果访问不包含重新调用模型生成、重新审查等耗用能力。具体收费功能白名单在实施前梳理完整。

### 3.2 充值增加期限

```text
grant_time = 首次成功发放权益的服务端时间
new_expires_at = max(old_expires_at, grant_time) + purchased_days × 24 小时
```

- 无旧期限或已经到期，从 grant_time 开始。
- 尚未到期，在旧到期时间上累加。
- 购买不同天数的套餐仍累计，例如剩余 10 天再买 90 天，剩余约 100 天。
- 使用整数天数，不接受负数、小数或用户上传的成交天数；范围建议 1～3650 天，需运营确认。
- 价格以人民币分保存，天数以套餐快照为准；客户端不能指定价格、用户或授权目标。
- 支付渠道 paid_at 保留原始财务含义；延迟回调建议从实际首次权益发放时刻开始，避免客户未获使用权却已经消耗天数。该规则需产品确认。
- 重复支付回调、主动查单、补单只能产生一次发放。同一用户并发支付锁定同一时长账户，顺序累加，避免丢天数。
- 到期判断采用 server_now < expires_at；显示剩余天数可向上取整，但不能用展示天数授权。
- 到期计算必须实时生效，不依赖定时任务把 active 改为 expired。

### 3.3 赠送、扣减与停用

- 运营赠送天数需要专用权限、原因和幂等标识；与充值共用期限累加规则。
- 扣减不能把不存在的未来权益当成可回收天数。误扣补偿用反向流水，不能删除原记录。
- 停用账号与暂停授权优先于剩余期限。建议停用期间自然时间继续流逝，是否冻结有效期是待确认规则。
- 第一版不做用户之间的天数转赠；原积分赠送不能直接改名成天数赠送。

## 4. 数据设计与迁移

### 4.1 应用配置

在 ClientAppModel 增加：

| 字段提案 | 说明 |
| --- | --- |
| model_access_mode | platform/local，默认 platform，建议数据库约束 |
| model_policy_version | 模式/策略修订版本，默认 1 |
| model_policy_updated_at | 最近一次模式策略变更时间，可与已有审计字段合理复用 |

应用级操作必须走已有客户端管理权限和访问范围校验；客户端业务接口仅从认证上下文取 app_id，不信任请求中的 app_id。

### 4.2 商品与订单快照

- 在共享模板、客户端刊例增加 `entitlement_kind: credits | duration`，默认 credits。
- 复用已有 `benefit_period_days`；模板对应已有 `billing_period_days`，界面统一叫“使用天数”。
- 兼容期 duration 仍可保留现有 `plan_type=subscription`，不增加到处传播的第三种 plan_type。
- duration 固定 total_credits=0、release_plan=[]；积分有效期等旧非空字段可保留兼容默认值，但不得参与校验、展示或发放。
- 本地时长套餐不能要求“已经存在有效订阅”才能购买，否则首次充值和过期续费会被阻断。
- 不可原地把已售出的 credits 刊例改为 duration；新建对应时长刊例，旧刊例下架保留历史。
- 订单增加快照字段：snapshot_schema_version、model_access_mode、entitlement_kind、policy_version、duration_days、授权功能版本（需要时）。
- 历史订单缺少新字段统一解释为旧 credits 语义，不能看当前应用模式推断。
- 第一版建议时长商品使用一个销售价格；如数据结构仍要求首购/续费价格，两者设为相同。duration 不走“跨套餐升级”价格或周期逻辑。

### 4.3 时长授权账本

复用现有订单、支付、退款体系；在 module_billing 内建立时长权益账本，不新增第二套支付系统。

建议新增：

1. `client_duration_account`：唯一键 app_id/user_id；expires_at、status、revision、最新流水引用。用于高效查询与并发加锁。
2. `client_duration_grant`：记录每笔订单或人工赠送的来源、原始天数/秒数、发放时刻、开始/结束区间、已撤销剩余量及状态；保留可追溯的来源。
3. `client_duration_ledger`：追加式记录 grant/refund/adjust/migration，含来源、幂等键、前后到期时间、变更秒数、原因、操作者和 created_at。

将秒数作为内部精确单位，可处理退款或迁移的不足一天；商品仍只销售整数天。一次权益变更必须在同一事务写 grant、ledger、account。所有写入保持统一的锁顺序，并对来源加数据库唯一约束。

订阅/用户概览接口按模式投影期限。不要同时让旧 SubscriptionModel 和新时长账户成为两个可独立写入的“真相”；local 以时长账本为准，旧订阅模型仅用于旧资产或兼容只读展示。

### 4.4 退款规则

- 金额退款与权益回收分开描述；是否可退、已使用部分如何计价需要业务确认，本文不制定退款条款。
- 权益预览需展示目标订单已使用时长、尚未使用时长、其他订单时长及退款后的到期时间。
- 第一版建议只自动回收目标订单对应的未使用时长；已使用部分不形成负时长，也不能自动侵占其他订单。
- 若顺序为 A 30 天、B 90 天，A 使用了 10 天后撤销 A 剩余 20 天：B 的剩余 90 天前移衔接；不能让客户等待原 A 的结束时间。
- 来源按发放顺序分配消费，回收后重排尚未消费的来源区间；保留原始快照和调整流水。不能只把 expires_at 减去订单原天数。
- 退款预览、审批、渠道成功后的权益执行均重新核验；并发充值与退款锁同一账户。
- 渠道退款成功但权益执行失败时进入现有补偿/修复队列，幂等重试并告警，不伪造“全部完成”。
- 金额部分退款如何映射天数未定义前，第一版不开放自动部分时长退款，由审核明确回收时长。
- 历史 credits 订单继续走旧退款算法，与 duration 分支隔离。

## 7. 双端接口

### 共同接口契约（提案 v1，两份方案保持一致）

新增 `GET /api/v1/client/runtime-config`，沿用现有 Bearer 鉴权和标准响应包络。以下仅为 data 的示例，不是已实现接口：

```json
{
  "schema_version": 1,
  "app_id": 1,
  "user_id": 100,
  "model_access_mode": "local",
  "policy_version": 3,
  "server_time": "2026-10-08T04:00:00Z",
  "refresh_after_seconds": 30,
  "authorization": {
    "status": "active",
    "can_start_task": true,
    "expires_at": "2026-11-07T04:00:00Z",
    "remaining_seconds": 2592000,
    "revision": 8,
    "recheck_after_seconds": 30
  },
  "billing": {
    "mode": "duration",
    "credits_enabled": false,
    "credit_pack_purchase_enabled": false
  },
  "local_model": {
    "configuration_allowed": true,
    "protocols": ["openai_compatible"]
  },
  "minimum_supported_client_version": null
}
```

- `model_access_mode`：`platform | local`；`billing.mode`：`credits | duration`，由服务端从模式推导，不设置互相冲突的独立开关。
- `authorization.status`：`active | not_purchased | expired | suspended`。用户被停用、应用停用或登录无效时优先沿用认证层的拒绝规则；有效会话下的授权暂停才使用 suspended。
- local 模式下，`can_start_task` 必须同时满足账号/应用有效、使用授权未暂停、服务端当前时间小于 expires_at。platform 模式继续执行现有平台业务规则，不能把新时长条件套到旧客户。
- `expires_at` 使用 UTC、带时区；无购买记录为 null。平台模式不使用本地时长字段阻断任务。剩余秒数仅辅助显示，精确到期时间才是依据。
- `policy_version` 在应用模式/策略变更时增加；`authorization.revision` 在充值、退款、人工调整、授权暂停等变更时增加。版本允许跳号，不依赖连续递增事件到达。
- `configuration_allowed` 表示当前已认证账号可以配置模型；建议未购买或已到期也可保存配置和执行受限连接测试，但不能运行收费业务任务。
- 登录成功并保存会话后立即拉取；恢复登录、切换账号、支付完成、窗口回到前台及联网恢复时重新拉取，正常在线时约每 30 秒刷新。
- 应用策略可按 app_id/version 缓存；用户授权必须按 app_id/user_id/revision 隔离，不能将整份响应缓存为应用级公共数据。客户端响应使用 no-store。
- 本地 Python 服务使用内存中的用户访问令牌自行获取并校验本接口；不能把 renderer 传入的 mode、can_start_task 或 expires_at 当作可信授权。
- 第一阶段建议采用在线授权：启动/恢复收费任务时实时核验，长任务在后续模型或收费工具调用前检查至多 30 秒的内存授权缓存；进程重启不复用离线授权，缓存失效且无法联网时暂停新的收费步骤。30 秒是建议值，需两端统一配置。
- 获取配置失败不得自动视为 local，也不得自动切回 platform；本地模型地址与 Key 不出现在此接口。
- 缺少新字段仅用于旧 platform 服务端兼容；非法枚举、身份不匹配、过期授权与未知协议版本不能按兼容逻辑放行。

### 7.2 其他接口调整

| 接口/能力 | 契约要求 |
| --- | --- |
| 现有客户端管理接口 | 增加模式、版本；编辑时带预期版本，过期更新返回冲突 |
| 模式切换预检查（新增） | 返回受影响对象数量、阻断原因、迁移批次、目标最低版本；不返回其他应用数据 |
| /client/billing/catalog | 增加 entitlement_kind、duration_days；local 仅返回适用时长商品及服务端报价 |
| 现有下单接口 | 只接受商品 ID、支付方式、幂等键、协议确认及预期策略版本；成交价格、天数由服务端决定 |
| 现有订单查询 | 增加权益状态 pending/applied/failed，支付成功不等于页面可推断权益成功 |
| 当前授权、时长流水（新增） | 当前授权可复用 runtime-config；流水单独分页接口 |
| 人工时长调整（新增） | 操作权限、目标用户、整数天数或受控修正秒数、原因、幂等键 |
| 退款预览 | 原权益来源、可撤时长、新期限、现金与权益处理状态 |

建议错误语义：DURATION_EXPIRED、DURATION_NOT_PURCHASED、APP_MODE_CHANGED、POLICY_VERSION_CONFLICT、CLIENT_UPDATE_REQUIRED、LOCAL_MODEL_NOT_ALLOWED。复用现有响应 code 约定实现机器可判别原因；中文 msg 仅面向用户，不能让客户端靠包含“积分不足”来判定所有失败。

## 8. 模式切换与存量迁移

### 8.1 切换不是直接改一个布尔值

采用“预检查 → 暂停新建订单 → 处理在途订单 → 准备迁移数据 → 提交策略版本 → 刷新缓存/恢复销售”的受控流程。无存量数据可简化，但所有请求仍检查最终模式与版本。

- 预检查提交携带期望策略版本；与下单共享清晰的并发控制边界，预检查后新出现订单不能漏掉。
- 未完成订单仅在切换确认框提醒，不再阻断。晚到支付记录真实收款；原订单权益类型与当前模式不一致时留待财务核对或退款，不自动转换或发放权益。
- 极端延迟到账按不可变订单快照履约，再进入明确补偿流程；不得直接吞款或发放另一种商品。
- 正在运行的平台请求按受理时的计费快照结算；下一次平台请求按新模式拒绝。

### 8.2 platform → local

1. 发布同时理解两种模式的新客户端，确认最低支持版本。
2. 创建 local 时长套餐与价格，准备切换后上架；旧积分套餐停止新销售。
3. 旧有效订阅是否迁移剩余时长需业务确认。若承接，应根据已经支付且未退款的权益时间区间做并集合并，包含已预付的未来周期，不能简单读取最近一个周期或累计重叠天数。
4. 迁移记录批次号、来源周期、秒数、切换基准时间与结果，幂等导入时长账本；不重复添加原有 local 时长。
5. 历史积分、待发积分仍按原订单合同履约、退款或经确认的迁移方案处理。新模式本身不自动暂停旧积分定时释放。
6. 不自动把余额按某比例换成天数；没有确认的换算和客户承接规则，不开放该类存量应用切换。

### 8.3 local → platform

- 检查平台模型、刊例、报价、积分发放及老版本兼容均就绪。
- 存在未用完的已购 local 时长时，默认阻止直接切换，直到有明确的承接、退款或补偿方案。
- 不清空时长账本，不凭 local 的有效期授予平台免费模型。
- 模式撤销后客户端保存的 Key 可保留为禁用状态，不远程读取或删除用户的密钥。

### 8.4 缓存与旧版本

应用缓存按策略版本失效，授权缓存按用户版本失效。后台修改后客户端正常在线最多一个刷新窗口发现；明确撤权响应立即生效。不能承诺离线客户端即时撤权。

旧客户端不能理解 duration，不得让其购买后卡在积分为零。通过版本能力校验与最低版本提示保护购买、配置和任务链路。版本号具体值在发布时确定，不虚构当前已支持版本。

## 11. 验收清单

### 11.1 自动化

- [ ] 默认迁移为 platform，已有订阅/积分包的价格、发放、预占、结算不变。
- [ ] 应用 A 的模式不能改变应用 B 的商品、授权、缓存和奖励。
- [ ] 非管理员、无应用访问权限的运营人员不能改模式或赠天数。
- [ ] duration 允许零积分和空释放计划；credits 仍执行旧约束；伪造商品模式失败。
- [ ] 未购买、已过期、未过期、不同天数套餐充值都按 max 公式计算。
- [ ] 同时支付两笔、重复回调、查单与补单竞态只各加一次。
- [ ] 支付已成功但发放失败可以幂等修复，订单页明确显示权益处理中。
- [ ] 到期边界、UTC 日期、闰日、剩余不足一天、延迟回调语义准确。
- [ ] 退款不侵占其他订单；顺序来源回收后连续衔接；重复退款不重复扣时长。
- [ ] 充值与退款并发后的账户期限和来源流水一致。
- [ ] 模式切换与下单并发可控；旧平台请求完成结算，新平台请求被拒绝。
- [ ] 历史订单缺少新字段按 credits 解释；旧积分定时任务不被全局停止。
- [ ] 零元商品不会重复无限延长；人工赠送权限、限值与原因完整。
- [ ] 退出、账号停用、应用停用与授权暂停优先于本地剩余天数。
- [ ] 未授权和旧客户端不能直接下单绕过界面。

### 11.2 界面与联调

- [ ] 本地模式看不到新积分配置、积分包或错误的模型成本必填。
- [ ] 共享价格模板保留其他客户端的积分能力。
- [ ] 用户详情、订单、退款预览和流水的到期时间一致。
- [ ] 登录、扫码登录、恢复登录、充值成功后客户端获取同一有效策略。
- [ ] 深浅主题、窄窗口、加载、空态、重复提交及失败重试可用。
- [ ] 语音/搜索等额外服务没有因模型模式变更意外免费开放。

在隔离测试环境执行现有 Ruff、pytest、前端类型检查与对应测试；不得对未知远程数据库直接运行迁移或支付测试。本次仅编写方案，以上均为未来验收项。

## 12. 风险与必须确定的业务决策

| 决策 | 建议默认值 | 不确定时的边界 |
| --- | --- | --- |
| 是否允许平台和自配混用 | 第一版互斥 | 不实施混合免积分 |
| 使用天数定义 | 连续 24 小时 | 不按登录次数扣减 |
| 套餐是否功能分级 | 第一版同功能、不同天数 | 不做等级升级折算 |
| 新用户是否赠送试用 | 不默认赠送，支持运营配置后扩展 | 不无限领取零元商品 |
| 退款金额与已用天数 | 另行确定，技术先支持准确预览 | 不自动推定全额/按比例退款 |
| 旧订阅如何承接 | 经确认后迁移未消费区间 | 不自动覆盖历史资产 |
| 本地模式离线使用 | 第一版不支持长期离线 | 授权过期后暂停新收费步骤 |
| 到期时运行中任务 | 完成已发请求并保存，阻止下一收费步骤 | 不强杀、不重置进度 |
| 账号停用时期限流逝 | 继续流逝 | 冻结需另有规则和流水 |
| 额外收费服务 | 单独授权，缺少方案时禁用对应入口 | 不放开平台免费调用 |
