# 财务运营中心

## 范围与验收

本次范围为财务概览、交易订单、异常待办、退款管理、推广提现、账单对账、渠道与账户，以及客户端订单/退款/权益状态。发票与独立报表不在本次范围。列表导出属于查账能力。

- 页面不显示重复的菜单标题或页面描述。沿用现有搜索栏、FaTable、状态 Tag、工具栏、分页、抽屉、主题和权限规范。
- 金额以整数分存储与聚合；统一人民币。日期范围按北京时间自然日，结束日期包含当天；概览按实际付款、退款、提现完成时间归属。
- 正式财务、对账及客户端订单记录排除历史开发演示脚本同时写入的 `dev-demo-order-*`、`DEV*` 订单号和 `DEVTRADE*` 渠道号，不删除原始演示数据。免费开通订单保留记录，但不计入渠道实收、成交订单数、客单价和付费转化；不能根据渠道开关将历史订单归属到另一渠道。
- 财务筛选栏收起时为三项筛选与操作按钮同排，展开后显示额外字段；样式仅用于财务中心，窄屏按可用宽度换行。渠道环图同时显示各渠道的实际金额。
- 全部业务读写按令牌当前客户端隔离；不能由请求参数指定其他客户端。公司账户中不属于当前客户端的交易不计入当前客户端收入。
- 订单提供服务端筛选、分页、明细及导出，不截断为最近500条。支付成功与权益发放分开核验。
- 未支付订单操作列的“更多”提供关闭与删除；已关闭未支付订单只提供删除。两项操作沿用 `workspace:finance:order:query` 权限，按当前客户端隔离，填写原因并记录审计；已付款订单通过退款处理。
- 退款支持部分/全额、申请、审核、拒绝、异步执行、查单、权益处理、奖励冲正与审计。提交退款先持久化稳定商户退款号；结果未知时保留退款占用额度，不创建新号重付。
- 退款申请需明确权益处理：保留权益（补偿）或终止该订单剩余权益。终止不扣除其他订单的积分；已消费或冻结积分明确展示，不能伪装已追回。部分退款不自动猜测按天折算。
- 对账保存任务、来源、账单日期、摘要、匹配结果与差异处理记录；真实下载渠道交易账单，校验来源/签名/摘要和文件大小。没有账单、下载失败与对账成功但零交易分别呈现。
- 渠道收款开关沿用渠道及客户端授权；提现/退款业务开关持久化到当前客户端设置并即时生效，环境配置作为部署就绪条件。关闭出款不阻止查询已发送的交易结果。
- 真实退款和提现操作不用于自动测试；测试使用隔离数据库和带签名的模拟渠道响应。正式渠道只做经授权的非扣款查验。

## 口径

收银台换购采用关联新订单：普通待支付订单不再锁定整个账号购买；同次换套餐/渠道传 `replaces_order_no`，建立新单后原单记录 `replaced_by_order_no`、撤下付款码并安排后台关单。原单支付状态仍以渠道核验为准；旧款到账保留实际收款、进入财务待核对，不重复发权益或自动退款。不同独立购买沿用各自报价；迟到的低等级或同等级异套餐积分订阅不会覆盖当前更高/同级订阅。参见[客户端接入说明](客户端收银台换套餐与支付切换接入说明.md)。

交易订单关闭调用 `POST /api/v1/finance/orders/{order_id}/close`，请求 `{"reason":"关闭原因"}`。只有渠道确认关闭才返回 200 与 `closed`；202 表示待核对，409 已付款时保留真实付款和权益。付款码隐藏后继续核验原订单，不能将超时当作关单成功。

支付宝未扫码预下单例外：成功发码时保存服务端付款码有效期；付款码到期并留出 1 分钟安全余量后，查到已验签的 `ACQ.TRADE_NOT_EXIST` 且无付款证据，可关闭本地业务订单。到期前的交易不存在仍待核对，不直接当作关单成功；未知历史付款码没有有效期证据时保持原核验策略。此分支不调用撤销或退款，也不修改已付款订单。具体规则见[客户端集成文档 7.2.1](客户端集成文档.md#721-取消购买超时查单与购买阻塞)。

删除未支付订单调用 `DELETE /api/v1/finance/orders/{order_id}`，请求 `{"reason":"清理原因"}`。删除前锁定当前客户端与订单，先查渠道并尝试关单；查到付款返回 409 且保存付款，已存在订阅周期、积分批次/账本、退款、已处理回调、非零渠道账单或推广事实时拒绝删除。可删除订单物理清理查单记录、未处理回调、该订单协议确认、异常、未入账账单行、旧订单审计及旧模式预览，并更新受影响账单摘要；只保留归档订单和一条删除审计供付款核对。归档订单不出现在订单列表、导出或购买阻塞检查中。

归档删除与渠道关闭分别记录：已确认关闭的归档单停止查单；结果未明的归档单按每天一次、每客户端每轮最多 5 笔低频核验，不重建已清理的查单日志。迟到的验签付款恢复原订单并幂等核对权益，取消过的模式切换需财务确认。已删除购买编号不能重用，真实重新购买须生成新幂等键。生产批量清理需先备份并固定订单 ID 清单，逐笔使用相同保护逻辑；不清除付款、余额或共享基础设施数据。

实收=周期内成功支付金额；退款=周期内渠道已确认退款金额；退款后净收款=实收−退款。提现支出独立列示。以上都不是企业账户余额或会计利润。渠道实际手续费仅取已核验账单，不用配置费率估算后冒充实扣金额。

渠道交易账单属于商户级数据。对账时先与本系统订单按渠道与商户单号关联，再按当前客户端展示；其他客户端交易不得暴露用户、商品或金额。未能归属的渠道交易仅作为商户级检查提示，不自动创建客户端订单。

| 退款管理 | 退款申请和已确认退款两个视图；全额/部分申请、保留或终止权益、审核、原单查单、原单重提；商户平台外部退款的核验同步；失败原因、审核与渠道处理时间、权益回收结果 |
| 推广提现 | 用户、收款渠道、脱敏收款账户、申请金额、审核时间、渠道流水、查单次数、下次核验、完成时间；审核/拒绝/查单/调用记录；全部在途与单一状态筛选 |
| 渠道对账 | 按渠道和账期下载真实交易账单；任务、文件摘要、支付与退款明细、渠道/系统金额、手续费、匹配差异、处理依据和处理人；失败任务可重试 |
| 异常待办 | 下单失败、已付款未发放权益、退款/提现结果未明、账单差异；优先级、认领、业务跳转、处理理由、核验关闭与重新打开 |

订单“核验”使用签名验证过的渠道查单结果。若已确认支付且该订单完全没有发放周期/积分，按原快照补发；存在退款流水或活动退款申请时不补发。补发与查单写审计，并持有当前客户端锁避免重复发放。

退款“结果未明”会继续占用可退金额，后台按原退款号查单。运营人员核对商户记录后可按原单重提，退款号、金额和原始参数保持不变。重提被拒绝也不代表此前未知请求一定失败，不释放其金额占用；只有确定终态才结账。首次提交的明确业务拒绝可标为失败，释放申请占用。

终止权益只回收原订单尚可用的积分、取消未释放批次及原订单周期。已经消费/失效的积分和执行中预留数量单列；执行中任务完成时，属于已终止批次的未用预留不会退回可用余额。其他有效订单维持自己的原始周期和积分。外部商户平台退款的核验同步仅同步资金与奖励，保留原权益；终止权益需使用平台退款申请流程明确审核，不能根据外部退款金额猜测比例。

终态下单失败可填写处理依据后关闭调查，不删除原失败订单；新的下单失败仍单独预警。其他资金未知/权益异常需恢复原业务或登记对账差异处理后才能核验关闭。账单差异处理保留渠道原始金额及原始匹配状态，不将人工说明伪装为自动一致。

## 配置与发布

此版本不新增支付私钥环境变量。既有 Alipay/WeChat 密钥和回调仍由后端运行环境提供；新增业务开关存在数据库 `finance_channel_control`，全局收款启用与客户端渠道授权沿用原表。环境中配置缺失不能通过页面开关补齐，页面不会接收私钥。

- 三个业务开关：进入财务中心 → 支付渠道 → 选择当前客户端对应渠道卡片。卡片的登记费率和结算周期是运营录入值，不代表渠道账单的实际扣费；概览手续费只累计已下载账单中的实值。
- 收款需全局渠道开启、当前客户端授权开启且环境配置就绪；退款/提现分别再受各自业务开关约束。暂停后停止新提交，已送渠道的请求继续查单。
- 本地和线上若连接同一数据库，共享这些业务开关与业务数据；本地环境文件不是数据库隔离开关。隔离联调必须使用独立数据库/Redis/测试渠道。
- 迁移 `20260910_finance_center` 接在 `20260909_catalog_codes` 后，创建6张财务表并补齐现有财务菜单/按钮权限。已有普通角色不会自动获得新的退款审核、对账、开关等权限，应在角色管理按职责分配；超级管理员可访问。
- 现有发布脚本已在切换后端前执行备份和 `python main.py upgrade --env=prod`。正式发布须同时更新后端和运营前端，客户端在该后端版本可用后发布。仅刷新浏览器或仅上传前端不能代替数据库迁移。
- 本版本禁止通过 Alembic downgrade 删除财务操作凭据。应用版本回退保留财务表；结构调整用新的前向迁移。有在途出款时须保留原单查询处理能力。
- 定时任务 `system_finance_maintenance` 每分钟调度，处理待退款、结果查询、账单下载与异常核验；通过任务管理查看运行状态。暂停业务开关不会关闭查询任务。

## 核对依据与验证边界

支付宝账单请求带 `secure=true` 获取HTTPS下载地址，依据[支付宝官方SDK接口说明](https://github.com/alipay/alipay-sdk-php-all/blob/master/v3/docs/Api/AlipayDataDataserviceBillDownloadurlApi.md)。退款请求和查询使用官方API；结果不明时原号重试，微信同一商户退款号只退款一次，参见[微信支付官方接口集合](https://www.postman.com/wechatpay-dev/wechat-pay-public-workspace/documentation/uxuwz5y/wechatpay-apiv3)。

自动验证采用临时SQLite、模拟Redis和模拟渠道响应，检查权限、用户/客户端隔离、退款额度占用与幂等、权益回收、两种积分结算、跨日统计、账单差异、迁移模型匹配及PostgreSQL离线DDL。实际商户签约权限、真实账单格式和资金到账仍需正式联调验证；未将隔离测试结果表述为真实退款/提现已成功。当前交付不包含线上部署。


## 2026-09-11 对账与订阅退款优化

- 渠道对账的“批量对账”默认昨天，支持连续 1–31 天和昨天/近7天/近30天快捷选择。后台按“当前客户端＋渠道＋账单日”逐日排队；已完成任务不重建，失败任务可按原日期重试。列表每5秒刷新正在处理的任务。
- `FINANCE_AUTO_RECONCILE=true` 默认启用自动创建昨日账单；`FINANCE_RECONCILE_HOUR=10` 为北京时间的触发小时。每分钟维护任务在指定小时后检查，只对当前客户端已授权启用、生产模式且配置就绪的渠道创建一次。页面显示配置的运行时间，“系统自动”为系统生成任务。自动任务失败后保留原因，由运营按天重试，不反复重下；停机跨过的更早日期可用范围补账。
- 上述变量通过后端环境配置生效；未运行 `system_finance_maintenance` 时不会自动处理。未开通的微信渠道不会自动请求账单。此项不新增数据库字段，无需新增迁移。
- 新的跨套餐购买从支付权益发放时立即生效，同套餐续费才接在当前到期日之后。原套餐的既有周期和积分批次保留原时间，不自动折价、转移天数或延长。新支付快照保存等级；历史快照缺少等级时回退原刊例等级。历史已存在订单不批量重写周期。
- 当前套餐从已支付、未退款且已到开始时间的周期中选择最高等级；同套餐连续续费合并显示到期时间。退款移除指定订单周期后重算：原专业版仍在有效期则恢复其原到期日，无有效周期则无有效订阅；未来续费不提前生效，到了开始时间由维护任务恢复。人工取消的订阅不会因为退款重新启用。
- 申请与审核均显示当前套餐、退款后套餐/到期时间、回收可用积分、取消待发放积分、在途预留及已消费/过期数量；预览指纹用于检测确认前发生的权益变化，变化时返回409并重新加载，不静默使用旧预览。申请和审核的预览记录到审计中。兼容旧调用方未传指纹的请求；正式页面始终传入。
- 权益只在渠道确认退款成功后处理，执行时按当时剩余额度重算，因此预览是当前时点估算。部分退款也可选择终止该订单全部剩余权益，不按退款比例自动折算。
- 客户端不再把已取消、已过期、未开始周期显示为当前套餐；订单详情核验到退款成功会刷新订阅与积分。支付提示按“权益已更新、积分按计划发放”表达，避免续费或分期发放被误认为一次到账。

新增接口：`POST /finance/bills/batch`（provider/start_date/end_date，复用对账管理权限）；`GET /finance/bill-automation`（对账列表权限）；`GET /finance/orders/{id}/refund-preview?action=retain|terminate`（退款申请权限）；`GET /finance/refunds/{id}/preview`（退款审核权限）。退款申请/审核增加可选 `preview_token`，客户端订单与订阅 API 结构保持兼容。
