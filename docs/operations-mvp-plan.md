# 喻信智能体运营平台首发 MVP 完整方案

## 1. 结论与产品边界

首发版采用“单运营团队、多客户端应用”的模式。

- 运营后台只有一个内部运营组织，不建设 SaaS 式多租户组织体系。
- 每个被运营的软件称为“客户端”或“客户端应用”，数据库统一使用 `client_app`、`app_id`、`app_code`。
- 所有客户端业务数据必须按 `app_id` 隔离；运营人员只能进入自己获授权的客户端。
- 顶栏头像左侧展示客户端切换器，不在侧栏顶部，也不提供“全部客户端”。
- 最终用户使用独立的 `client_user`，不复用运营人员表 `sys_user`。
- 价格体系是全平台模板；产品刊例、定价策略、用户、订单、订阅、积分、模型绑定、用量和运营事件归属于当前客户端。
- 模型供应商、密钥与模型目录只在运营端维护；客户端只读取可用模型并通过运营端网关调用。
- 首发不做经营概览、不做审批流、不做动态产品能力编排、不做“全部资源”、不做自动续费扣款。
- 商机资源只保留真实空状态界面，不生成演示商机。

## 2. 信息架构

### 2.1 全局

- 客户端切换：顶栏头像左侧，显示当前客户端；切换后换发带 `app_id` 的运营令牌，并重新加载当前页面数据。
- 编辑刊例、定价策略、用户、客户端或模型配置时切换客户端，必须先确认丢弃未保存内容。
- 无可用客户端：拒绝进入应用业务页，提示联系管理员授权。
- 不设置“全部客户端”：跨客户端汇总以后由专门的经营分析接口完成，不能通过取消隔离实现。

### 2.2 首发菜单

| 中心 | 页面 | 首发范围 |
| --- | --- | --- |
| 预算中心 | 价格体系 | 平台级版本与套餐模板，草稿/发布/归档 |
| 预算中心 | 客户端管理 | 新增客户端、基础资料、状态、运营人员授权 |
| 预算中心 | 产品刊例 | 当前客户端的对外套餐、售价、积分和释放计划 |
| 预算中心 | 定价策略 | 当前客户端的首购/续费/通用限时价格 |
| 预算中心 | 订阅与积分 | 当前客户端的订单、订阅周期、积分余额 |
| 用户运营 | 用户管理 | 组合筛选、状态与资料管理、临时密码、积分调整、详情档案和标签 |
| 资源中心 | 模型管理 | 供应商、密钥、模型目录、客户端绑定、业务路由 |
| 资源中心 | 商机资源 | 页面骨架与真实空状态 |
| 财务中心 | 支付渠道 | 微信支付、支付宝平台启停与当前客户端授权 |

经营概览放在后续阶段，首发不展示入口。其余已有菜单可以保留为规划项，但不能伪造业务数据。

## 3. 数据与权限设计

### 3.1 认证主体

| 主体 | 表 | 令牌用途 | 权限范围 |
| --- | --- | --- | --- |
| 运营人员 | `sys_user` | 登录运营后台 | 菜单权限 + `sys_user_app` 客户端授权 |
| 客户端用户 | `client_user` | 登录投标客户端 | 固定客户端能力，不授予后台权限 |
| 模型运行令牌 | 不落用户表 | OpenWorker 短时调用模型 | 仅模型网关，绑定 `app_id`、`user_id`、过期时间 |

运营 API 的 `app_id` 只能从当前令牌取得，不能信任查询参数、请求体或前端缓存。即使是超级管理员，进入客户端业务页也必须先选定客户端。

### 3.2 客户端与用户

- `client_app`：客户端代码、名称、版本、状态、是否开放注册与显示排序；列表、切换器和登录默认选择均按“排序、ID”稳定排序。
- `sys_user_app`：运营人员可访问的客户端与默认客户端。
- `client_user`：客户端最终用户，用户名在同一客户端内唯一。
- `client_user_tag`：人工标签；自动分群首发由详情聚合结果表达，不建立复杂规则引擎。
- `client_auth_event`：客户端注册、登录、失败与限流安全事件，不保存密码和令牌。

用户管理列表负责账号、联系方式、订阅、积分、支付、注册/活跃时间与可操作字段，并支持订阅、套餐、积分区间、标签和时间组合筛选；用户详情聚合基础档案、标签、订阅周期、订单、积分批次、项目数、模型用量和登录安全事件。这样保留老板原型里的“分群与档案”价值，又不把档案页误当用户管理。

### 3.3 预算、订阅和积分

- `pricing_standard_version`、`pricing_plan_template`：平台级价格体系与模板。
- `app_catalog_plan`：当前客户端实际销售刊例，引用已发布模板，但价格与积分独立维护。
- `app_pricing_strategy`：当前客户端限时策略；首购、续费专属规则优先于通用规则，重叠生效会被拦截。
- `payment_order`、`payment_callback`：下单快照、金额、渠道、支付回调与幂等处理。
- `pay_channel`、`app_payment_channel`：平台商户渠道与客户端可用授权分离；客户端只能使用同时完成平台启用和当前客户端授权的渠道。
- `payment_attempt`：下单和主动查单尝试审计，用于定位渠道故障和回调丢失。
- `subscription`、`subscription_cycle`：当前订阅与每次购买形成的不可变权益周期。
- `credit_account`：余额汇总。
- `credit_grant`：按套餐释放计划形成的积分批次和有效期。
- `credit_ledger`：不可变积分流水。
- `credit_reservation`：模型调用前预占、完成后按实际用量结算，异常超时自动释放。

积分不是单一可修改余额。订阅支付成功后按批次释放；调用模型时先预占，成功后结算，多退少补；同一请求号不得重复扣费。人工调整必须记录原因和操作人。

### 3.4 模型资源

- `model_provider_template`：平台供应商表单模板，内置常用供应商并允许自定义。
- `model_provider_account`：真实供应商账号和加密密钥；不向客户端返回。
- `model_catalog`：平台模型目录与成本计价。
- `app_model_binding`：客户端可用模型、售价倍率/积分计费和是否允许用户选择。
- `app_model_route`：按业务场景配置主模型与回退模型。
- `model_usage`：每次调用的令牌、费用、积分与状态。

每条用量会固化当次供应商成本金额，后续调整模型目录价格不会改写历史成本，经营概览可据此计算真实毛利。

供应商可以直接在运营页面新增。预设负责描述字段结构，运营人员填写真实 Base URL、API Key 和扩展配置；系统不创建假账号、假密钥或假模型。

## 4. 关键业务流程

### 4.1 客户端用户使用模型

1. 用户使用 `app_code` 和账号登录，获得客户端访问/刷新令牌。
2. 客户端读取 `/client/model/config`，只得到允许展示的模型和业务路由。
3. OpenWorker 请求短时模型运行令牌，密钥全程留在运营端。
4. 网关校验用户、客户端、订阅/积分和模型绑定，预占预计积分。
5. 网关通过进程级上游连接池向真实供应商发起请求，并以 SSE 保持流式输出；余额不足以覆盖请求上限时先自动下调最大输出，连最小输出也无法覆盖才拒绝。
6. 完成后按实际 token 成本结算积分并记录用量；失败或客户端中断则按实际结果结算并退回多余预占。
7. 主模型失败时按当前客户端业务路由尝试回退模型。

该链路保留客户端现有流式体验，不把供应商网络、计费或密钥管理转嫁给桌面端。

### 4.2 客户端支付订阅

1. 客户端读取当前 `app_id` 的在售刊例与有效价格。
2. 用户提交带幂等键的支付订单。
3. 运营端冻结套餐、价格、策略和积分释放规则快照，再调用微信/支付宝官方下单接口。
4. 支付平台回调运营端；验签、商户身份、金额、订单和重复回调校验全部通过后才激活订阅。
5. 创建订阅周期和积分批次，客户端轮询订单状态后刷新权益；若渠道回调丢失，轮询会以受控频率主动查单并补偿权益。

零元体验订单不调用支付渠道，但仍走同一幂等订单、订阅周期和积分批次流程。首发只支持一次性支付和手动续费；自动续费必须等签约、解约、扣款重试和通知流程完整后再开放。

订阅到期、积分批次到期、分期积分释放和陈旧预占回收由系统周期任务每 5 分钟执行一次，并在相关读接口访问时补偿执行；任务按明确 `app_id` 逐个处理，可重复执行且不重复发放权益。

生产环境密钥全部通过后端环境变量和密钥文件提供，不落库、不返回前端。支付宝启用前必须配置应用 ID、签约卖家 ID、公私钥；微信启用前必须配置 AppID、商户号、商户私钥、API v3 密钥，以及与回调 `Wechatpay-Serial` 对应的平台证书或微信支付公钥。正式上线前还必须使用真实商户沙箱或小额订单完成下单、回调、重复回调和查单补偿验收。

`SECRET_KEY` 同时保护登录令牌和运营端保存的模型供应商密钥。生产环境会拒绝默认值或短密钥启动；上线后必须纳入密钥备份且保持稳定，未经密钥迁移不得直接轮换。

### 4.3 运营数据回传

客户端通过本地 SQLite outbox 可靠保存事件，后台异步批量上报：

- 项目创建、归档、恢复；
- 文档导入；
- 审查启动；
- 文档任务成功/失败；
- 客户端启动/停止；
- 模型配置同步。

事件使用稳定 `event_id` 幂等，失败指数退避，只有运营端完整确认后才删除。上报元数据采用白名单，不上传文档内容、提示词、文件名、路径、密钥或完整令牌。模型 token 和费用由网关自身记录，不依赖客户端上报。

未来经营概览只消费这些真实数据和订单/订阅/用量事实表，不反向侵入客户端核心流程。

## 5. API 分层

- 运营认证：登录结果包含可访问客户端；切换客户端时换发令牌。
- 客户端认证：`/client/auth/*` 与 `/client/user/*`。
- 运营用户管理：`/client-users/*`，统一按当前令牌 `app_id` 查询。
- 客户端套餐与积分：`/client/billing/catalog`、`/client/billing/account`、`/client/billing/subscription`、`/client/billing/ledger`。
- 客户端支付：`/client/payment/capabilities`、`/client/payment/orders`。
- 支付回调：`/payment/callback/wechat`、`/payment/callback/alipay`。
- 客户端模型配置：`/client/model/config`。
- 模型调用：`/client/runtime/token`、`/runtime/model/complete`、`/runtime/model/stream`。
- 运营事件：`/client/telemetry/events:batch`。

所有响应继续使用现有标准包络；流式模型接口使用 SSE，不套普通 JSON 包络。

## 6. 分阶段交付计划

### P0：数据边界与认证（首发阻断项）

- 客户端表、运营人员授权、令牌 `app_id`、顶栏切换器。
- 默认客户端为“招投标智能体”（稳定编码 `bid_agent`）；登录后自动选择有权限列表中的第一项，未选中时顶栏只显示“选择客户端”。
- 独立客户端用户认证与后台用户管理；注册/登录按客户端、IP 和账号限流并保留安全事件。
- 跨客户端越权测试、无客户端上下文拒绝测试。

### P1：收费闭环（首发阻断项）

- 价格体系模板、客户端刊例、定价策略。
- 支付渠道客户端授权、支付订单、微信/支付宝回调与主动查单补偿、订阅周期、积分批次和流水。
- 幂等下单/回调、余额并发、积分预占/结算/超时释放测试。

### P2：模型集中管理（首发阻断项）

- 供应商模板与真实账号、模型目录、客户端绑定、业务路由。
- 客户端只读模型设置、短时令牌、普通与 SSE 调用、失败回退。
- 密钥脱敏、跨客户端模型隔离和扣费一致性测试。

### P3：运营数据底座（首发应完成）

- 隐私白名单事件、客户端 outbox、批量幂等接收。
- 用户详情聚合真实行为、订阅、订单、积分、用量。
- 商机资源空状态。

### P4：上线前验收

- 空库和存量库迁移演练、初始化幂等检查。
- 运营端和客户端全量类型检查、单测、构建。
- 指定浏览器下进行浅色/深色、桌面宽屏与 375px 移动宽度视觉回归。
- 使用真实测试商户完成最小金额支付回调；使用真实模型账号完成流式对话和扣费核对。
- 灰度发布一个内部客户端，观察错误率、支付回调、积分对账和模型延迟后再放量。

## 7. 上线验收标准

- 切换客户端后，用户、刊例、策略、订阅、积分、订单、模型绑定、用量和事件均不可串读。
- 客户端用户不能获得运营后台菜单或超级管理员能力。
- 未配置真实模型时明确显示不可用，不能回退到客户端自填密钥。
- 有积分且路由有效时可直接流式使用；余额不足在调用前明确拒绝。
- 重复订单、重复支付回调、重复事件和重复结算不会重复发权益或扣积分。
- 支付渠道未同时完成平台启用和当前客户端授权时，客户端不能发起该渠道订单。
- 运营端不持久化文档正文、提示词、文件路径或供应商明文密钥。
- 价格模板发布不自动修改现有客户端刊例；订单使用不可变快照。
- 商机资源无数据时显示真实空状态，经营概览不进入首发菜单。

## 8. 明确延后

- 经营概览与跨客户端经营分析。
- 自动续费签约、扣款、重试、解约和通知。
- 审批流、动态产品能力/成果配置。
- 自动分群规则引擎和营销触达。
- 商机资源后端、全资源统一搜索。
- 发票、退款、对账单和财务结算自动化。

这些能力以后基于现有事实表和 `app_id` 边界增量建设，不需要推翻首发数据模型。
